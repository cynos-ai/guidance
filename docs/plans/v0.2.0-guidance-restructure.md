## 1. Purpose

Restructure Cynos Guidance into one small, universal system prompt plus multiple independently triggered Skills organized by responsibility.

The current unreleased `0.2.0` draft combines general expression rules, project-owner assumptions, research presentation, decision facilitation, Socratic discovery, and stress testing inside `project-owner-communication`. That solved one local Skill conflict but produced a package that is too specific to software project owners and too internally coupled.

The target architecture must support broad human–AI communication while preserving `engineering-judgment` as a separate domain Skill. Communication Skills must control dialogue scenarios only; they must not own software engineering work.

## 2. Product boundary

Cynos Guidance is an umbrella Pi package, not a communication-only package and not an engineering-only package.

It contains:

1. **Always-on guidance:** a compact cross-domain behavior and communication baseline.
2. **Communication Skills:** independently triggered dialogue modes for broadly applicable interaction scenarios.
3. **Domain Skills:** independently triggered task judgment for a specific domain, beginning with software engineering.
4. **Harness adapters:** thin integrations that expose the same guidance and Skills to a host, beginning with Pi.

Keep these public identities unchanged:

- Product: `Cynos Guidance`
- npm package: `@cynos-ai/guidance`
- GitHub repository: `cynos-ai/guidance`

Update the product description from coding-project-specific language to:

> Portable system guidance and cohesive on-demand Skills for AI agents.

## 3. Why this change

### 3.1 Observed failures

The current communication Skill was used during technical research and design discussion, but its outcome-first presentation rules were diluted by a mechanically sequential interview flow. Specific failures included:

- an intended finished video was silently narrowed to intermediate shot material;
- reversible defaults were repeatedly presented as confirmation questions;
- vendor and model names appeared before the capability model they served;
- no stable end-to-end model anchored later decisions;
- one Skill controlled both expression and several incompatible dialogue workflows.

### 3.2 Root cause

Two independent axes were merged:

- **Expression:** how every response should be presented to the user.
- **Dialogue mode:** how a particular conversation should ask questions and converge.

The Skill was also scoped to a software project owner even though most expression rules apply to general human–AI interaction.

### 3.3 Design response

- Move compact, broadly applicable expression rules into always-on guidance.
- Split dialogue workflows by independently recognizable user intent.
- Keep software engineering judgment in a sibling domain family.
- Do not create Skill dependencies or a base communication Skill that every dialogue mode must co-load.

## 4. Target architecture

```text
principles/
└── core.md

skills/
├── communication/
│   ├── guided-discovery/
│   │   └── SKILL.md
│   ├── decision-support/
│   │   └── SKILL.md
│   └── stress-test/
│       └── SKILL.md
└── engineering/
    └── engineering-judgment/
        └── SKILL.md

extensions/
└── pi.js
```

The grouping directories `communication/` and `engineering/` must not contain `SKILL.md`. Pi recursively discovers directories containing `SKILL.md`, so commands remain flat:

```text
/skill:guided-discovery
/skill:decision-support
/skill:stress-test
/skill:engineering-judgment
```

Keep `package.json#pi.skills` as `./skills`; do not enumerate individual Skills.

## 5. Ownership model

| Owner | Responsibility | Must not own |
|---|---|---|
| `principles/core.md` | Cross-domain grounding, shared intent, response organization, evidence labels, correction handling, question threshold, and stop behavior | Detailed dialogue workflows or domain procedures |
| `guided-discovery` | Clarify an ambiguous goal, problem, idea, requirement, or desired outcome | Selecting among already-defined options or attacking an existing plan |
| `decision-support` | Help choose among viable options using criteria, evidence, trade-offs, and a recommendation | Performing the underlying domain work or open-ended goal discovery |
| `stress-test` | Challenge an existing plan, argument, strategy, or design to expose material failure modes and validation needs | Normal explanation, neutral option selection, or implementation |
| `engineering-judgment` | Perform substantive software engineering work with repository fit, safety, evidence, and a stop condition | General dialogue style or non-engineering decisions |
| `extensions/pi.js` | Inject core guidance once and expose package resources through Pi metadata | Content policy, routing logic, tools, network access, or enforcement |

When multiple responsibilities apply, they compose rather than override each other:

```text
Domain Skill      → what task work and evidence are required
Dialogue Skill    → how this conversation advances
Always-on core    → how each response is grounded and presented
User instruction → explicit desired depth, cadence, and artifact format
```

## 6. Always-on guidance specification

Rewrite `principles/core.md` as a cross-domain baseline. Keep it below 2 KB and in English.

It must express these behaviors without a fixed response template:

1. Ground claims and decisions in available context; inspect discoverable facts before assuming or asking.
2. Establish the intended outcome and material constraints; do not silently narrow the outcome to fit a preferred method, tool, provider, or intermediate artifact.
3. Match the user's domain knowledge; preserve precise standard terminology and explain only necessary private or project-specific terms.
4. Lead with the answer, outcome, or observable effect; disclose mechanisms, evidence, and exhaustive detail progressively.
5. Distinguish verified fact, inference, recommendation, unknown, unavailable evidence, and blocked work when the distinction affects trust or action.
6. Treat user corrections as updates to the shared model and revisit dependent conclusions before continuing.
7. Ask only questions whose answers change the path; use reversible low-risk defaults and reserve explicit confirmation for material or hard-to-reverse consequences.
8. Answer simple requests directly; do not turn them into discovery, decision, or stress-test ceremonies.
9. Apply conversational organization to assistant dialogue only. A user-requested artifact must follow its own audience, format, and project conventions.
10. Use the smallest sufficient proof and stop when the requested outcome is satisfied or remaining uncertainty has a bounded next step.
11. Preserve safety, trust boundaries, data, compatibility, and explicit failure handling where relevant; prompt text is not a security control.

Remove explicit Skill-routing sentences from the core. Pi already exposes each Skill's name and description in its system prompt. Routing belongs in frontmatter descriptions.

## 7. Communication Skill specifications

All communication Skills must be domain-neutral. Examples may mention a plan, product, article, purchase, study topic, strategy, or technical choice, but must not assume a code repository or project owner.

### 7.1 `guided-discovery`

**Job:** Help a user turn an unclear goal, problem, idea, requirement, or desired outcome into a clear outcome contract and a bounded set of unknowns.

Proposed frontmatter:

```yaml
---
name: guided-discovery
description: "Use when a user wants help clarifying an ambiguous goal, problem, idea, requirement, or desired outcome through guided questions before choosing a solution. Uses Socratic inquiry and scenario walkthroughs; stops once the outcome, boundaries, and material unknowns are clear."
---
```

Required behavior:

- Start from the user's desired observable result, not an available mechanism.
- Use Socratic lines selectively: clarification, assumptions, evidence, alternatives, implications, and reframing.
- Move from wide questions to narrow questions as ambiguity decreases.
- Walk a representative end-to-end scenario when abstract wording hides an outcome mismatch.
- When the outcome spans multiple meaningful stages, actors, or transformations, create one stable end-to-end model labeled by observable results or responsibilities. Reuse and update that same model after corrections instead of replacing it with disconnected diagrams or lists. Do not force a model onto a simple request.
- Group independent questions; ask one at a time only when an answer determines the next branch or the user requests that cadence.
- Carry reversible defaults forward without ceremonial confirmation.
- Maintain a compact state containing outcome, non-goals, constraints, corrected assumptions, and material unknowns.
- Stop before implementation selection unless choosing a solution is explicitly requested; hand that state to `decision-support` when a real choice remains.

### 7.2 `decision-support`

**Job:** Help a user make a defined choice among viable options using explicit criteria, evidence, trade-offs, and a recommendation.

Proposed frontmatter:

```yaml
---
name: decision-support
description: "Use when a user needs to choose among viable options or make a consequential decision and would benefit from explicit criteria, trade-offs, evidence, and a recommendation. Organizes the decision without taking over unrelated domain work."
---
```

Required behavior:

- Restate the decision and intended outcome before comparing options.
- Derive a small set of decision-changing criteria from that outcome.
- Compare only credible options; include deliberate inaction only when it is genuinely viable.
- Organize complex choices as situation → options → criteria → comparison → recommendation.
- Lead with a recommendation when evidence is already strong.
- Present capabilities or responsibilities before vendor, model, tool, or implementation names.
- Separate verified facts, reasoned assessments, and items requiring a test or PoC.
- When external evidence affects the decision, prefer primary sources; date volatile claims; state price currency, unit, tier, and assumptions; treat unavailable evidence as unavailable rather than negative proof; and convert material unknowns into bounded tests or PoCs.
- Maintain decisions, rationale, rejected options, and remaining validation needs without repeating the full register every turn.
- Stop when the decision is actionable or the remaining unknown has a bounded validation step.

This Skill may organize vendor or model selection, but it does not own web research, pricing verification, experimentation, or implementation. Those responsibilities remain with tools or future domain/task Skills.

### 7.3 `stress-test`

**Job:** Rigorously challenge an existing plan, argument, strategy, or design and return material risks, mitigations, and validation needs.

Proposed frontmatter:

```yaml
---
name: stress-test
description: "Use when a user asks to challenge, grill, red-team, or run a premortem on an existing plan, argument, strategy, or design to expose material assumptions, failure modes, mitigations, and validation needs."
---
```

Required behavior:

- Establish the proposal and intended outcome before attacking it.
- Treat “grill me” as a request for rigor, not automatically as one-question-at-a-time pacing.
- Select the lightest effective method: assumption probe, adverse scenario, premortem, counterexample, or strongest credible alternative.
- Follow dependency chains one question at a time; group independent questions.
- State what decision each material question tests and provide a recommended answer when evidence supports one.
- Rank findings by impact and plausibility instead of exhausting remote edge cases.
- Preserve rejected assumptions unless new evidence reopens them.
- Close with the strongest surviving plan, material residual risks, mitigations, and next validation steps.
- Stop when further challenge is unlikely to change the plan or validation strategy.

The legacy global `grill-me` Skill in the canonical maintainer environment has been removed, so `stress-test` is the sole owner of “grill me” behavior for this project. Before qualitative behavior review, check the active Pi Skill inventory for another overlapping user-installed Skill and disable that local overlap for the review. Do not weaken the public `stress-test` trigger or add package compatibility logic for unrelated global installations.

### 7.4 Deferred communication modes

Do not add `guided-learning`, brainstorming, coaching, interview, research-briefing, Five Whys, rubber-duck, or separate Socratic/premortem Skills in `0.2.0`.

Reasons:

- `guided-learning` has a plausible independent outcome but no observed failure or trigger boundary has yet been validated in this project.
- Socratic questioning and premortem are methods inside an outcome-owned Skill, not standalone package responsibilities.
- Research briefing mixes task evidence gathering with presentation; the universal core plus `decision-support` owns the currently observed communication need.
- Additional modes should pass the same admission gate after real use demonstrates an independent trigger and useful standalone result.

## 8. Engineering Skill specification

Move the existing Skill without changing its public name:

```text
skills/engineering-judgment/
→ skills/engineering/engineering-judgment/
```

## 9. Remove and redistribute the current communication Skill

Delete:

```text
skills/project-owner-communication/
```

Do not retain a compatibility stub or base communication Skill. A stub would preserve overlapping ownership and could still co-trigger with the new scenario Skills.

Redistribute current content as follows:

| Current content | Target owner |
|---|---|
| Direct answer, outside-in order, progressive detail, audience calibration | `principles/core.md` |
| Do not narrow the user's outcome; correction updates the model | `principles/core.md`, detailed in `guided-discovery` |
| Question threshold and reversible defaults | `principles/core.md`, specialized cadence in each dialogue Skill |
| Socratic inquiry and scenario walkthrough | `guided-discovery` |
| Decision state, options, criteria, recommendation | `decision-support` |
| Vendor names after capability roles; fact/assessment/PoC distinction | `principles/core.md` and `decision-support` |
| Grill, premortem, red-team, assumption challenge | `stress-test` |
| Project-owner audience assumptions and software-project-specific examples | Remove |
| Formal artifact boundary | Keep an explicit compact rule in core: conversational organization does not override a requested artifact's audience, format, or project conventions |
| Research evidence discipline | Keep the fact/assessment/PoC distinction in core and the primary-source, date, price-unit, unavailable-evidence, and bounded-validation rules in `decision-support` |
| `research-briefing.md` as a separate workflow | Remove; do not create a replacement Skill in this release |

## 11. Test changes

### 11.1 Recursive Skill discovery

The current package test assumes every immediate child of `skills/` is a Skill. Replace it with recursive discovery of directories containing `SKILL.md`.

The expected public Skill map is:

```json
{
  "engineering-judgment": "skills/engineering/engineering-judgment/SKILL.md",
  "guided-discovery": "skills/communication/guided-discovery/SKILL.md",
  "decision-support": "skills/communication/decision-support/SKILL.md",
  "stress-test": "skills/communication/stress-test/SKILL.md"
}
```

Validate:

- exactly these four public Skills are discovered;
- immediate parent directory matches frontmatter `name`;
- frontmatter contains exactly `name` and `description`;
- descriptions begin with `Use when` or `Use for` and stay within the Agent Skills limit;
- every relative Markdown link resolves within the owning Skill directory;
- grouping folders contain no `SKILL.md`;
- no duplicate names exist.

### 11.2 Core tests

Keep the 2 KB limit and English-only check. Remove the assertion that core text contains every Skill name; the core must not manually route Skills.

### 11.3 Behavior probe inventory

The current JSON is a review-case inventory, not a semantic test runner. Do not claim that CI validates model routing or response quality.

Replace `test/trigger-cases.json` with `evaluations/behavior-probes.json`. Give every probe:

- a stable ID;
- one or more input turns;
- expected Skill routing;
- expected observable behavior;
- forbidden behavior;
- the boundary being exercised: positive, negative, adjacent, ambiguous, conflict, or over-following.

CI may validate only the JSON schema, referenced Skill names, and presence of boundary coverage. It must not call an LLM or fail a commit because of nondeterministic model output.

Minimum qualitative probes:

| Prompt | Expected routing |
|---|---|
| “Help me clarify what I actually want from this trip.” | `guided-discovery` |
| “Use Socratic questions to help me define the argument of this article.” | `guided-discovery` |
| “Which of these three tools should I buy for my team?” | `decision-support` |
| “Compare these model providers and recommend one for this outcome.” | `decision-support`; research tooling may also apply |
| “Grill me on this launch plan.” | `stress-test` |
| “Run a premortem on my study strategy.” | `stress-test` |
| “Fix this intermittent authentication bug.” | `engineering-judgment` |
| “Help me choose a migration path, then implement it.” | `decision-support` + `engineering-judgment` |
| “Explain recursion in one paragraph.” | no dialogue Skill; core presentation only |
| “Write this API reference in the repository's formal style.” | artifact conventions control; no conversational style leakage |

Add probes for the original failures and over-following boundaries:

- a finished-video outcome is not narrowed to intermediate shot material;
- reversible defaults do not produce repeated confirmation questions;
- capabilities and responsibilities precede vendor or model names;
- a user correction updates dependent conclusions;
- one stable end-to-end model is reused across a multi-turn correction;
- discovery stops before solution selection when not requested;
- decision support does not perform unrelated implementation;
- stress testing stops after material branches;
- engineering judgment does not activate for non-engineering plans.

Run selected probes manually when reviewing a material prompt/Skill release. Recording a model run is optional evidence, not a CI gate.

### 11.4 Pi integration proof

Do not add `@earendil-works/pi-coding-agent` as a dependency or devDependency in `0.2.0`. The published package does not import Pi, and preserving a zero-dependency package is more valuable than putting host integration into unit tests.

CI must deterministically validate the package manifest, recursive Skill layout, frontmatter, links, tarball contents, and prompt injection behavior using Node's built-in test runner.

Before release, use an already installed Pi to run `DefaultResourceLoader` manually against both the source tree and an unpacked npm tarball. Record the Pi version and require:

- four expected public Skills;
- one extension;
- zero Skill diagnostics;
- zero extension errors;
- project-local `.pi/skills/` excluded from the tarball.

If Pi is unavailable, report this release check as blocked; do not silently call it passed. Keep prompt injection idempotency in deterministic CI tests.

## 12. Implementation sequence

An implementing agent must follow this order:

1. Read `AGENTS.md`, `.pi/skills/guidance-authoring/SKILL.md`, its admission checklist, `.pi/skills/skill-authoring/SKILL.md`, and its audit checklist.
2. Confirm the working tree is clean and `package.json` remains at unreleased `0.2.0`. Check the active Pi Skill inventory for an overlapping `grill-me`; the canonical maintainer copy has already been removed.
3. Rewrite `principles/core.md` to the specification in section 6.
4. Move `engineering-judgment` into the engineering grouping directory without changing its content.
5. Delete `project-owner-communication` and its references.
6. Create the three communication Skills from section 7 in English.
7. Rewrite deterministic tests for recursive discovery and the new expected Skill set. Do not add Pi or an LLM test dependency.
8. Replace trigger cases with the behavior probe inventory and review at least one positive, adjacent, conflict, and over-following case per Skill without treating model behavior as deterministic CI.
9. Update `AGENTS.md`, both READMEs, `package.json`, and `package-lock.json` metadata.
10. Run all acceptance checks in section 13.
11. Audit every new or moved Skill using the project checklists. Fix blocking and important findings.
12. Commit and push the implementation, then wait for CI.
13. Do not create `v0.2.0` or publish npm until the project owner reviews the implemented prompt and Skill contents.

Avoid unrelated cleanup, build-system changes, new dependencies, or release-workflow changes.

## 14. Risks and controls

| Risk | Control |
|---|---|
| Always-on core becomes a communication handbook | Keep it below 2 KB; move workflows and examples into Skills |
| Communication Skills repeatedly co-trigger | Give each a different starting state and stop condition; test adjacent routing |
| Socratic questioning becomes mechanical | Select only decision-changing questions; stop when outcome is clear |
| Stress testing becomes endless or adversarial | Rank by impact and plausibility; require a final surviving plan and stop condition |
| Decision support takes over domain work | State the boundary in frontmatter and body; compose with domain Skills |
| Grouping folders break discovery | Use recursive structural tests plus a manual pre-release Pi loader check |
| A user-installed `grill-me` conflicts with `stress-test` | Keep one owner in the maintainer environment; check active Skills before qualitative review rather than weakening package ownership |
| Removal of `project-owner-communication` surprises early users | Publish a migration table for `0.2.0`; do not preserve an overlapping alias |
| Future contributors add arbitrary Skill families | Require guidance admission evidence and an independent trigger/outcome |
