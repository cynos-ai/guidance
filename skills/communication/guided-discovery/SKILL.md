# Guided discovery

Turn an unclear starting point into a shared outcome contract without prematurely choosing a solution.

## Build the outcome contract

- Start with the observable result the user wants, who or what experiences it, and what would count as complete.
- Separate the outcome from an example, mechanism, provider, intermediate artifact, or solution the conversation happened to begin with.
- Capture material non-goals, constraints, corrected assumptions, and unknowns that could change the outcome.
- Treat a user correction as a state update. Revisit every conclusion that depended on the corrected assumption before continuing.

Do not perform this setup as a ceremony when the user's intent is already clear. State the current understanding compactly and move to the first unresolved point.

## Ask decision-changing questions

Use only the line of inquiry needed to remove material ambiguity:

- **Clarification:** What does success mean in observable terms? What is in or out?
- **Assumptions:** What must be true? Which belief is being treated as a fact?
- **Evidence:** What supports or could cheaply disprove the current understanding?
- **Alternatives:** Could a different framing produce the same intended outcome?
- **Implications:** What changes for affected people, systems, cost, safety, or future choices?
- **Reframing:** Has a proposed solution displaced the actual problem?

Start wide when the user knows the domain and needs room to define the goal. Narrow the question as the remaining ambiguity becomes specific.

- Group a small set of related, independent questions.
- Ask one at a time only when an answer determines the next branch or the user explicitly requests that pace.
- State what each material question will clarify.
- Recommend a reversible, low-risk default instead of requesting ceremonial confirmation.
- Inspect discoverable facts rather than asking the user to provide them.
- Once an answer is inferable, state it and update the shared state instead of continuing the interview.

## Walk the outcome end to end

Use a representative scenario when abstract language hides a mismatch between the stated goal and what a proposed route would actually deliver.

When the outcome spans multiple meaningful stages, actors, or transformations:

1. Create one compact end-to-end model labeled by observable results or responsibilities.
2. Use it to locate missing boundaries, handoffs, and assumptions.
3. Reuse and update that same model after corrections; do not replace it with disconnected diagrams or lists.
4. Keep model, vendor, class, or implementation names out of the primary model unless they are themselves part of the user's outcome.

Do not force a model onto a simple request.

## Maintain handoff state

Keep a compact state containing:

- intended outcome and completion signal;
- material non-goals and constraints;
- corrected or rejected assumptions;
- unresolved questions and validation needs;
- the stable end-to-end model when one exists.

Show only the changed part during normal turns. Summarize the full state at a major correction, a transition, or the close.

## Boundary and stop

Do not select among already-defined options, attack an existing plan, or start implementation unless the user expands the request. Preserve the discovery state so a later decision or task process can reuse it without replaying the conversation.

Stop when the outcome, boundaries, and material unknowns are clear enough for the user's next action. Do not continue asking from a generic checklist.
